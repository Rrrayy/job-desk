## 1. 版本目标

### 1.1 一句话

**v1.0.0 = 求职主流程闭环 + 数据格式对外承诺稳定。**

在此之前，产品管的是「投出去之后、拿到 Offer 之前」这一段：投递 → 沟通 → 笔试 → 面试 → 结果。`status` 里有 `offer` / `onboarded` 两个状态，但**一个字段都没记薪资、期限、职级**——产品在最需要做决定的那一步断掉了（见 PRD §5.3「已发 Offer → 提示确认到岗日期、天数、薪资」，这句话从 v0.1 欠到现在）。v1.0.0 要补的是：

> 投递 → 面试 → **Offer → 比较 → 选择 → 入职** —— 一条完整管线，每个节点都有数据、都能回看。

同时做三个「补洞」动作：公司维度从「6 个字段」变成「能打开的档案」；录入成本从「填 2 个字段」降到「说一句话」；看板上的红色角标从「只能看」变成「能一次清掉」。

### 1.2 「1.0.0」对用户到底承诺什么

不是「功能更多了」，而是一句话：**你的数据格式从这一版起稳定，后续升级不会再让你手工搬数据。**

| 承诺 | 落到可验证的机制 |
| --- | --- |
| 数据只增不减 | `migrateV5ToV6` 只改 `schemaVersion` 一个字（§4.6），不重命名、不删除、不搬数据 |
| 升级可回滚 | 沿用 §D.2 契约：迁移前整份写回滚点，失败三出口，`schemaVersion` 只增不减 |
| 导出可互换 | v6 导出文件在 v1.0.x 全系列可导入；v5 备份导入 v1.0.0 走同一条迁移函数 |
| 依赖不膨胀 | 本版**不新增任何第三方依赖**；日期解析、加权计算、分组全部手写（§1.3） |
| 网络不扩张 | 全应用 `fetch` 仍只在 `gateway.ts`；模块三**纯本地规则**，一次请求都不发（§3.3） |

### 1.3 三个硬约束的落实方式（方案不得违反）

| 约束 | 本版怎么守 | 预算 |
| --- | --- | --- |
| **单文件 ≤ 1 MB** | 四模块合计新增代码 ≤ 95 KB；不引入图表库（进度条用 `<div>` 宽度）、不引入日期库（复用 `lib/date.ts`）、长文案走「一句话 + tooltip」，不塞说明书 | 736 → **目标 ≤ 831 KB**，留 ~190 KB 给文案与修复 |
| **纯 localStorage** | 模块三**不落草稿**（关闭即丢，重打一句话的成本低于一套草稿表）；模块一/二只做 `Application.offer` 嵌套 + `Company` 加字段，不建新表 | Offer ≈ 300 B/条，600 家 + 300 Offer ≈ **+180 KB**，远低于 4 MB 水位 |
| **零新依赖 / 唯一网络出口** | 模块一的 AI 辅助（P1）**复用既有网关**，不新开出口，`check:no-network` 门槛不放宽；模块三明确**禁止调用 AI** | 新增 `fetch` = 0 行 |

> **体积预算拆分**：M1 决策台 30 KB · M2 公司档案 25 KB · M3 快记 18 KB · M4 沉默清单 12 KB · 共用组件 10 KB = **95 KB**。开发中若某模块超预算 30%，先砍它的 P1，不许动总闸（0.10.0 抬闸的教训）。

### 1.4 关于「1.0.0 的发布条件」（需拍板，见 §7 Q1）

`PRD-v0.2` §A.5 写过：**v1.0.0 的发布条件 = schema 连续 3 个 MINOR 未变 + 2 位外部贡献者合并过适配器**。实际是：v0.8 / v0.9 / v0.10 连续三个 MINOR 里 `schemaVersion` 从 2 一路升到 5，外部适配器贡献仍是 0。也就是说**原条件一条都没达成**。

我的建议：**按本次决策发布 1.0.0，但把这个偏差写进 CHANGELOG**，并用可验证的东西替代原条件：

- 替代「schema 连续 3 个 MINOR 未变」→ **本次迁移是「空迁移」**（只改版本号），并补 `migrateV5ToV6` 幂等 + 无损自动化测试；v6 起承诺「下一个 MAJOR 前不再改变既有字段语义」。
- 替代「2 位外部贡献者」→ **不可替代，只能承认**。诚实的表述是「1.0.0 指的是**数据格式**稳定，不是社区成熟度达标」，README 与 Release Notes 都不许暗示后者。

## 3. 需求池

> 验收标准一律写成「可断言的事实」。凡是「体验流畅 / 更清晰 / 更方便」都不算验收。

### 3.1 模块一 · Offer 决策台

**入口（不加一级导航，理由见 PRD §E.1）**：① 今日视图「N 个 Offer 待决策」卡片（`status ∈ {offer}` 且未做决策时出现）；② 看板「已发 Offer」列头右侧「对比 N 个 ▸」；③ 投递详情抽屉的 Offer 区块「去对比」；④ 决策完成后今日出现只读卡「你 3/12 选了字节 · 理由：成长」。

| 编号 | 功能 | 说明 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| OFF-1 | Offer 详情录入 | 抽屉内新增「Offer」区块：计薪方式（月薪/日薪）、月薪、薪数、日薪、签字费、股权原文、职级、单程通勤分钟、备注。**全部选填**，任一字段可单独保存 | P0 | 只填「月薪 20000」也能保存成功；刷新页面后该值仍在；九个字段全部留空时区块折叠为「+ 补录 Offer 信息」一行 |
| OFF-2 | 并排对比表 | 面板顶部一条可勾选的投递 chip 条（默认全选，上限 8 个，超出按收到 Offer 时间取最近 8 个并提示），表格横向滚动并排显示：综合分、四维分数、薪资结构、年薪合计、城市、职级、通勤、截止剩余天数 | P0 | 表头列数 = 勾选数；勾选 <2 个时对比区 disabled 且提示「至少选 2 个才能对比」；勾选第 9 个时 chip 条拒绝并提示；8 列时只有表格内部横向滚动，页面主体不出现横向滚动 |
| OFF-3 | 加权综合分 | 四维（薪资 `salary` / 成长 `growth` / 城市 `city` / WLB `wlb`）各打 1–5 分；权重 0–100 且四项和恒为 100 | P0 | 权重 30/30/20/20、四维均 5 分 → 综合分 = 100.0；权重同上、四维 3/4/5/2 → 综合分 = **70.0**（`3/5×30 + 4/5×30 + 5/5×20 + 2/5×20`，保留 1 位小数）；同分时顺序按显示顺序稳定，不抖动 |
| OFF-4 | 缺失维度处理 | 某 Offer 只评了 2 维时，不按 0 分参与，而是**按已评维度归一**并在格内标注 | P0 | 权重 30/30/20/20，只评 salary=5、growth=5 时综合分 = 100.0 且格内显示「按 2/4 维归一」；四维全未评时综合分显示 `—`（不是 0） |
| OFF-5 | 权重调节面板 | 4 个滑块，拖动任一滑块后其余三项**按原比例分摊剩余值**，整数化用最大余数法（余数相等时按 `salary→growth→city→wlb` 顺序取先者），和恒为 100 | P0 | 原 30/30/20/20 把 salary 拖到 60 → 其余为 **18/11/11**（合 100，整数）；对任意拖动序列，「四项和为 100 且每项为 0–100 整数」的断言成立 |
| OFF-6 | 记录最终选择 | 选定一个 Offer + 理由标签（内置 8 个：`pay/growth/city/wlb/team/brand/conversion/deadline`，可自由追加自定义，共 ≤5 个）+ 一段话（≤500 字）+ 被放弃的 Offer 多选 | P0 | 保存后刷新仍在；再次保存时先二次确认「改选会覆盖 3/12 的记录」；同一时刻至多一条决策（`db.offerDecision` 单对象，无数组） |
| OFF-7 | 回看 | 决策完成后：面板「我的选择」tab 常驻展示；今日视图展示一条只读卡（公司 + 决策日 + 理由首行 + 「改选」） | P0 | 把系统时间调到决策日 +180 天后打开今日，卡片仍显示且日期文本为绝对日期（不显示「6 个月前」这类相对文案） |
| OFF-8 | 决策不改状态 | 记录选择**不自动**改 `status`；对被放弃的 Offer 提供「一键标记已放弃」但**不自动执行** | P0 | 保存决策后，所有相关投递的 `status` 与 `statusChangedAt` 逐字段不变；点「一键标记已放弃」才写 `dropped` 并生成 system note |
| OFF-9 | 截止与缺项提醒 | 复用 `deadlineAt`（**不新增 Offer 专有截止字段**）+ `deadlineWarnDays`；缺分数维度的提醒走本地规则 | P0 | `deadlineAt` 距今 ≤3 天时面板顶部与今日各出现一条琥珀提示，文案含剩余天数；某 Offer 缺 ≥1 维时对比表格内该行标「还有 N 维没评」 |
| OFF-10 | 决策导出 | 导出为 Markdown 一段（含对比表 + 权重 + 选择与理由），可直接贴给家人/朋友看 | P1 | 导出文本粘到任意 Markdown 渲染器表格完整；含「本地加权计算，仅供参考」一行 |
| OFF-11 | AI 漏项检查（可选） | 用户主动点击才发请求，只输出「你可能没考虑的问题清单」，**不打分、不排序、不建议选谁** | P1 | 未配置 AI 时按钮置灰并提示去设置；生成文本不含阿拉伯数字分数、不含「建议选」；`npm run check:no-network` 仍绿；默认关闭 |

### 3.3 模块三 · 自然语言快记

**入口**：「＋记一家」弹窗顶部新增一行输入框「⚡ 一句话快记（例：明天下午 3 点字节二面）」，快捷键 `Q` 聚焦。**复用同一弹窗，不新增浮层。**

**解析链路（三步，第二步不可跳过）**：`输入 → 本地规则解析 → 确认条（逐字段可改） → 用户点保存 → 复用既有写库方法`。

| 编号 | 功能 | 说明 | 优先级 | 验收标准 |
| --- | --- | --- | --- | --- |
| CAP-1 | 一句话 → 确认条 | 解析结果以 chip 形式展示：意图 / 公司 / 岗位 / 时间 / 轮次 / 形式 / 状态建议，每个 chip 可点开改 | P0 | 输入「明天下午3点字节二面」→ 确认条显示 意图=面试、公司=字节跳动、时间=明天 15:00、轮次=2；点「保存」前 `localStorage` 与保存前**逐字节相同**（断言未写库） |
| CAP-2 | 时间规则 | 支持：今天/明天/后天/大后天、周X/下周X、`M月D日`、`M/D`、`D号`、上午/中午/下午/晚上/凌晨、`HH:mm`、`H点`、`H点半` | P0 | 「明天下午3点半」→ 15:30；「下周三上午10点」→ 下周三 10:00；「3月14日」→ 当年 3-14；表里 12 条样例逐条断言 |
| CAP-3 | 时间缺失不猜 | 只有日期没有时刻 → **不生成日历事件**，只生成 note 草案并提示「补个时间就能进日历」；只有时刻没有日期同理 | P0 | 输入「字节明天面试」→ 不产生 `Interview`、不产生 `CalendarEvent`；提示可见；确认条上时间 chip 显示「未定」 |

## 4. 数据字段设计

> 命名沿用 `types.ts`：英文小驼峰，可选字段 `?`，时间 ISO 8601 / 纯日期 `YYYY-MM-DD`。**每加一个字段都要能回答「用户在什么场景下填它」——填不动的字段不进来。**

### 4.1 模块一：`Application.offer`（嵌套，不建新表）

**为什么不建 `offers` 表**：一条投递 = 一个岗位 = 最多一个 Offer（同一岗位不会被发两次 Offer）。建表只会得到一个 1:1 外键 + 一套「孤儿 Offer 怎么显示」的新问题。嵌套与既有 `Application.sync` 同模式，**迁移成本为零**（缺失即不存在）。

```ts
/** 四维自评键。枚举只增不改（改动要过 maintainer 讨论） */
export type OfferScoreKey = 'salary' | 'growth' | 'city' | 'wlb';

/** 计薪方式：日常实习按天给钱，校招/全职按月。缺省按月 */
export type OfferPayMode = 'monthly' | 'daily';

/** Offer 详情。★ 全部可选 —— 拿到口头 offer 时用户只知道公司名 */
export interface OfferDetail {
  /** 计薪方式，缺省 'monthly' */
  payMode?: OfferPayMode;
  /** 月薪（元/月，税前）。整数 0–1,000,000 */
  monthlySalary?: number;
  /** 一年发几个月（12–24）。**年终奖已含在薪数里，不另设字段** */
  salaryMonths?: number;
  /** 日薪（元/天）。payMode==='daily' 时用 */
  dailyRate?: number;
  /** 签字费（元，一次性） */
  signOnBonus?: number;
  /** 股权/期权原文，≤60 字。**不折算成钱** —— 上市前的估值谁都不该假装算得准 */
  equityText?: string;
  /** 职级原文（"P5" / "T1.2" / "SP"）。自由文本，不做枚举 */
  level?: string;
  /** 单程通勤分钟数。整数 0–240 */
  commuteMin?: number;
  /** 四维自评分 1–5。缺 = 未评（**不按 0 分参与**） */
  scores?: Partial<Record<OfferScoreKey, 1 | 2 | 3 | 4 | 5>>;
  /** 补充说明 ≤200 字 */
  notes?: string;
  /** 本区块最后编辑时间（ISO）。编辑**不写 note**、不动 lastActivityAt */
  updatedAt: string;
}
```

| 字段 | 用户什么时候填 | 不填会怎样 |
| --- | --- | --- |
| `payMode` / `monthlySalary` / `salaryMonths` / `dailyRate` | 收到书面 offer 那天，对着 offer letter 抄 | 对比表该列显示「薪资未填」，综合分按剩余维度归一 |
| `signOnBonus` | 有就填，没有就不填（0 ≠ 未填） | 年薪合计不含它 |
| `equityText` | 打包价里含股权时抄原文 | 年薪合计旁标注「不含股权」 |
| `level` | 知道就问 HR，不知道不填 | 该行留空 |
| `commuteMin` | 已经租好房 / 决定住宿舍时算一次 | 该行留空 |
| `scores` | 决策前一周打分（这是决策台的核心动作） | 该维不参与，综合分标「按 N/4 维归一」 |
| `notes` | 想记「HR 说试用期 6 个月」这类 | 无 |

**派生（不落库）**：`annualTotal = monthlySalary × salaryMonths + signOnBonus`（仅 `payMode==='monthly'` 且前两者均有值时计算；标注「不含股权、不含绩效浮动」）。

### 4.2 模块一：`db.offerDecision`（顶层单对象）

```ts
/** 最终选择。★ 单对象而非数组 —— 一个人一次只能选一个 Offer；改选即覆盖（带二次确认） */
export interface OfferDecision {
  /** 选中的投递 → Application.id */

  reasonTags: string[];
```

写入时机只有一处：决策台「保存选择」。**不改任何 `Application.status`**（OFF-8）。

### 4.3 模块一：`settings` 新增

```ts
// AppSettings 新增（additive，缺省即默认）
```

### 4.4 模块二：`Company` 扩充（+5 字段，全部可选）

```ts
/** 融资阶段。'unknown' 显式表示「查过但没查到」，与「没填」区分 */
export type CompanyStage =
  | 'angel' | 'a' | 'b' | 'c' | 'd' | 'listed' | 'unknown';

export interface Company {
  /* —— 既有 —— */
  id: string;
  name: string;
  shortName?: string;
  industry?: string;
  city?: string;
  referrer?: string;
  /** 面试体感（面试官风格、流程快慢）—— 与下面 employeeReview 不是一回事 */
  impression?: string;
  createdAt: string;
  /* —— v1.0.0 新增（全可选） —— */
  /** 规模原文，"1000-9999人"。自由文本，不做枚举（各平台分档不一致） */
  scale?: string;
  /** 融资阶段（枚举）。缺省 = 没填 */
  financingStage?: CompanyStage;
  /** 官网，http(s):// 开头，≤200 字 */
  website?: string;
  /** 行业细分，≤40 字。"本地生活 / 到店" */
  industryDetail?: string;
  /** 员工口碑（听来的、看到的），≤300 字 */
  employeeReview?: string;
}
```

> `scale` 是**补回 `PRD.md` §8.1 已承诺但代码里缺失**的字段（文档与实现漂移），不算新需求。
> `impression` 与 `employeeReview` 必须分成两个字段：前者是「我面完的感觉」，后者是「这家公司怎么样」。合成一个字段的结果是用户永远只填一种。

### 4.5 模块三、模块四：**零 schema 变更**

| 模块 | 为什么不加字段 |
| --- | --- |
| 三 · 快记 | 解析全在内存，产物是既有实体（`Interview` / `Note` / `status`）。**草稿不落库**：一句话的输入成本低于维护一套 `captureDrafts` 表的成本，且草稿会带来「过期草稿怎么清理」的新问题 |
| 四 · 沉默清单 | 复用的全是既有字段：`mutedUntil`（静音）、`silenceOverride`（自定义阈值）、`Note.type:'followup'`（催问留痕）。批量操作只是循环调用既有写库方法 |

### 4.6 迁移 `5 → 6`

```ts
/** v1.0.0：纯版本号迁移。★ 什么都不写 —— 不凭空造权重、不补空 offer、不填 Company 新字段 */
export function migrateV5ToV6(input: unknown, ctx: MigrateContext): MigrateResult;
```

| # | 契约 | 怎么验 |
| --- | --- | --- |
| 1 | **空迁移**：`migrateV5ToV6` 唯一改动是 `settings.schemaVersion: 5 → 6` + 写 `lastMigration` | 对真实 v5 导出做迁移，除这两处外逐字段 deep-equal |
| 2 | **幂等**：`migrate(migrate(x)) === migrate(x)` | 对已是 v6 的输入直接返回原对象（引用相等亦可） |
| 3 | **缺省即默认**：`offerWeights` 缺失时由代码兜底 `{salary:30,growth:30,city:20,wlb:20}`，**不写进库** | 迁移后 `settings.offerWeights === undefined`，但 UI 显示 30/30/20/20 |
| 4 | **不为旧数据造内容**：旧 `Company` 不会获得空的 `scale: ''` 之类占位 | 断言新字段在旧数据上为 `undefined`（不是 `''`/`null`） |
| 5 | **先备份后改 + 三出口** | 沿用 §D.2 全套（回滚点、失败页、只增不减、不改 storage key） |
| 6 | **回滚阅读**：v0.10.0 打开 v6 数据 | v0.10.0 读到 `schemaVersion: 6` 走既有降级路径（空数据界面 + **不丢数据**），文案改为「这份数据来自 v1.0.0 或更新版本，请升级工具」 |

**`validateV2` 扩展（必须同步，否则「导出 → 导入」会挂，参考 §D.3 枚举扩张的教训）**：

| 位置 | 规则 | 越界行为 |
| --- | --- | --- |
| `offer.payMode` | `'monthly' \| 'daily'` | 字段级错误「第 N 条投递的 Offer 计薪方式不认识」 |
| `offer.scores` 的 key | `OfferScoreKey` 白名单 | 未知 key 丢弃并计一条 warning（不阻断导入） |
| `offer.scores` 的 value | 1–5 整数 | 越界清空该维（不阻断） |
| `offer.monthlySalary` / `dailyRate` / `signOnBonus` | 有限非负整数，上限 1,000,000 | 越界清空（不阻断） |
| `offer.salaryMonths` | 12–24 整数 | 越界清空 |
| `offer.commuteMin` | 0–240 整数 | 越界清空 |
| `offer.equityText` / `notes` | 60 / 200 字 | 截断 + 提示（沿用 §D.4「不静默丢」） |
| `company.financingStage` | 7 值枚举 | 清空该字段（不阻断） |
| `company.employeeReview` | ≤300 字 | 截断 + 提示 |
| `settings.offerWeights` | 四个 key 均为 0–100 整数且**和为 100** | 和≠100 时按比例归一后使用，并计一条 warning（**不阻断**） |
| `offerDecision.applicationId` | **不校验存在性** | 悬空是设计的一部分：投递被删后决策仍在，显示「（投递已删除）」，绝不能因此让整库导入失败 |

### 4.7 体积与性能

| 对象 | 单条估算 | 上限 |
| --- | --- | --- |
| `Application.offer`（全字段填满） | ≈ 300 B | 300 个 Offer ≈ 90 KB |
| `Company` 新增 5 字段（全填满） | ≈ 200 B | 600 家 ≈ 120 KB |
| `db.offerDecision` | ≈ 800 B | 单条 |

一年内 600 家 + 300 Offer ≈ 主库增加 210 KB，仍远低于 4 MB 水位（§D.4）。**真正的风险不是这些字段，而是 `employeeReview` 被当成日记写**——用 300 字硬上限挡掉。

```
│ 股权         │ 4 年 30 万        │ —              │ —                        │
│ 城市 / 职级  │ 北京 · P5         │ 北京 · L6      │ 北京 · —                 │
│ 通勤         │ 45 分钟           │ 20 分钟        │ 70 分钟                  │
│ 答复截止     │ 3/16（4 天）      │ 3/15（3 天）   │ 3/20（8 天）             │
│ 已评维度     │ 4/4               │ 4/4            │ ⚠ 3/4（分数已归一）      │
├──────────────────────────────────────────────────────────────────────────────┤
│ 这是按**你**的权重算的，不是我们推荐谁。        [ 记录我的选择 ]  [ 导出 ]    │
└──────────────────────────────────────────────────────────────────────────────┘
```

**几处刻意的设计**：

- **综合分下面必须摊开每一维的贡献**。只给一个总分就是「黑箱替你排序」；摊开之后，用户看到「快手成长满分但城市 2 分」，才知道该改的是哪一维的判断，而不是怀疑算法。
- **※ 归一化会让「少打分」的 Offer 分数虚高**：快手只评了 3 维却是 70 分，比评满 4 维的美团（72 分）只低 2 分。这是归一化的数学后果，不是 bug —— 所以「已评维度」必须单列一行、缺维的格子里写「未评（不计入）」而不是留空。留空会被读成「这维不重要」，而事实是「你还不知道自己怎么看这一维」。
- **日薪不给年薪合计**。`200/天 × 3 天/周 × 4 周` 得到的数字是不可比的（没算寒暑假、没算实际到岗），算出来反而误导 —— 这一格写「不能算」比写一个假数字诚实。
- **「调权重」在标题栏，不在表格里**。权重是「我的价值观」，一次调完后一直生效；放进表格会让人误以为每次对比都要重调。
- **底部一行免责**：`这是按你的权重算的，不是我们推荐谁` —— 这句防止用户把工具当算命。

**关键交互决策**：

| 场景 | 交互 | 理由 |
| --- | --- | --- |
| 一进来就显示解析结果 | 停止输入 400ms 后解析，**不按回车** | 回车在既有弹窗里是「保存」，不能让一句话改变既有肌肉记忆 |
| 保存前必须有一次确认 | 解析结果永远是「草案」，`保存` 是唯一写库动作 | 本地规则必然有误判。**猜完直接落库的代价是用户要自己去清理脏数据**，而清理的成本远高于多点一次 |
| chip 而不是重新生成 | 每个 chip 独立可改，改一个其他不动 | 用户最常见的动作是「就差公司名」，不该为了改一个词重打整句 |
| 状态建议默认不勾 | 涉及终态（`rejected`/`dropped`）一律默认不勾 | 误标「已挂」会让这条管线被塞进「已结束」列，用户很难发现 |
| 失败态给两条出口 | 「改用手动记录」+「就记成一条随手记」 | 前者是快速放弃，后者保证「我确实想记但语法怪」的内容不丢 |

**三条读图规则**：① 分组只按**等级**（红 / 黄），静音条目不单独成组，它留在自己那一组里、整行灰显 + `⌛` 角标 —— 否则「7 条」这个数字会随静音状态变化，用户对不上账；② 红组里 15 天处只画一条分割线，不建子组；③ 内推条目的阈值 ×3（`channelFactor`），所以「内推 10 天」是**黄**不是红，界面必须按实际等级归组，不能按天数硬切。

**批量催问的两步（最重要的一条）**：


为什么必须两步：`lastActivityAt` 是沉默计算的基准。**「我生成了话术」不是沟通事件，「我发了消息」才是。** 一步到位会让用户在自己根本没发的情况下把 7 条记录全刷成绿色 —— 那是在骗自己（同 `PRD-v0.2` §B.8 拒绝用抓取时刻刷新活动时间的理由）。

### 5.5 关键交互汇总（跨模块）

| 场景 | 交互 | 理由 |
| --- | --- | --- |
| 新增入口 | 三处都**不加一级导航**：决策台 = 全屏面板、公司档案 = 全屏抽屉、沉默清单 = 列表二级 tab | 三者都是「事件驱动」（拿到 offer / 想了解一家 / 周末清账），不是每日必看。6 个 tab 再加会挤爆 1440px（`PRD-v0.2` §E.1 结论不变） |
| 面板关闭 | 决策台与公司档案都走 `Esc` 关闭 + 记住滚动位置 | 用户是「看完一个再看下一个」，跳页会丢上下文（同 PRD §9.4） |
| 全部写操作 | 复用既有 `api`：`setStatus` / `addNote` / `createInterview`，不新开写库路径 | 自动继承撤销栈、冲突检测、时间线 system note，四模块零重复实现 |
| 空态 | 决策台无 Offer：「还没有 Offer。先在投递详情里补一条 offer 信息，或者把某条投递标成『已发 Offer』」；公司档案无面试：「这家还没约过面试」 | 沿用 PRD §10：空态必须给下一步，不许只写「暂无数据」 |
| 键盘 | `Q` 聚焦快记输入框；决策台 `←/→` 切 tab；沉默清单 `Space` 勾选当前行、`J/K` 上下移动 | 批量清账是键盘操作场景（几十行要勾），纯鼠标会劝退 |

## 6. 明确不做的

### 6.1 模块一

| 不做 | 为什么 |
| --- | --- |
| **不联网抓薪资数据**（Offershow / 脉脉 / 看准网） | ① 这些站都没有公开 API，抓取等于绕过对方协议（同 `PRD-v0.2` §B.1 的 F1–F4）；② 我们的隐私承诺是「零请求」，为了一个参考数字破掉这张准入证，成本远大于收益；③ 薪资样本天然有偏差（只晒高薪），拿来对比反而误导 |
| **不让 AI 替用户排序或推荐「选哪个」** | 决策的错误成本由用户承担，工具没资格替他做。AI 只能做「你可能漏了这几个问题」这种**提问**，且必须用户主动点、结果不含分数与结论（OFF-11 的验收条款就是在锁这件事） |
| **不自动把股权折算成钱、不给日薪折算年薪** | 未上市股权的价值取决于你信不信那个估值；日薪折算依赖实际到岗天数。算出来的假精度会让用户以为自己在做理性决策 |
| **不做「多轮 offer 谈判记录」** | 用户量太少（实习生几乎没有议价空间）。真要记，`offer.notes` 写一句就够，不值得一套结构化字段 |
| **不在决策后自动改状态 / 自动拒掉其他 offer** | 记录选择 ≠ 已经拒了别人。自动改状态会在用户还没通知 HR 时就把管线画成完成态（OFF-8） |

### 6.2 模块二

| 不做 | 为什么 |
| --- | --- |
| **不联网抓公司信息**（规模、融资、评分、工商信息） | 与模块一同一条理由。而且公司信息变化快，抓一次的快照半年后就是错的，「纯本地的旧数据」比「联网的新数据」更危险地像真的 |
| **不做公司合并/去重（本版）** | 合并是**破坏性**操作：两条投递、面试、笔记要重新挂靠，一旦错了无法回滚到用户满意的状态。本版只做「同名提醒」（COM-6），把判断权留给用户 |
| **不做组织架构 / 面试官人脉图** | 学生求职场景里这些数据没人填，强行建表只会得到一张永远空着的表 |
| **不做「公司与公司之间的对比」** | 那是模块一的活（对比的是 Offer，不是公司）。两处都能比，用户会不知道用哪个 |

### 6.3 模块三

| 不做 | 为什么 |
| --- | --- |
| **不调用 AI 解析** | 硬约束第 4 条：模块三必须是本地规则。另外 AI 解析一句话的延迟（1–3 秒）和不确定性，比本地规则差；本地规则至少**可预测、可测、离线可用** |
| **不猜完直接落库** | 这是本模块最重要的一条。宁可多点一次「保存」，也不要用户事后在 30 条记录里找哪条被记错了 |
| **不解析多句 / 不做对话式追问** | 一次一句话，超出部分明确提示「一次记一件」。做多轮追问会变成一个小型 NLP 产品，和「3 秒记一家」的原始目标背道而驰 |
| **不落草稿** | 一句话的重打成本约 5 秒；维护 `captureDrafts` 表要处理「草稿过期 / 草稿冲突 / 草稿要不要导出」，投入产出完全不成比例 |
| **不承诺语义理解**（比如「感觉这家稳了」→ 自动标 offer） | 情绪表达不是事实。词典命不中就老老实实说没听懂 |

### 6.4 模块四

| 不做 | 为什么 |
| --- | --- |
| **不自动发送催问消息** | 没有后端、没有平台接口（`PRD-v0.2` §B.1），也不可能做。产品只负责「生成话术 + 复制」，发送永远由用户在 BOSS 里手动完成 |
| **不做定时自动放弃**（「30 天没动静自动标放弃」） | 沉默不等于死了。有的内推流程就是慢（所以才有渠道系数 ×3）。自动改终态是不可逆的破坏 |
| **不做「催了几次」的独立计数器** | 时间线里的 `followup` note 已经是计数事实，再落一个字段就有两个真相来源（改一个忘一个是必然） |
| **不做沉默归因分析**（「你沉默率高是因为投得太泛」） | 这是没有依据的推断。工具不该对用户的求职策略下判断 |

### 6.5 全局

- **不加一级导航**（仍是 6 个 tab + 二级），**不引入任何依赖**，**不新增网络出口**，**不做 PWA / 推送 / 多端同步**（PRD §1.3 边界不变）。
- **不做 v1.0.0 专属的「新功能引导」长文案**：体积预算要留给功能，首次触达用一句 inline hint 代替三步引导。

## 7. 待确认问题（附默认建议，不阻塞开发）

| # | 问题 | 我的默认建议（可直接照此实现） |
| --- | --- | --- |
| Q1 | 本版直接发 `1.0.0`，但 `PRD-v0.2` §A.5 的发布条件（schema 连续 3 个 MINOR 未变 + 2 位外部贡献者）一条都没达成。发 1.0.0 还是 0.11.0？ | **发 1.0.0**，并在 CHANGELOG 明写「1.0.0 指**数据格式**稳定，不代表社区成熟度」。理由：本次是**空迁移**（只改版本号），格式风险最低的一版正好适合立承诺；继续 0.x 反而给用户「随时会变」的错误暗示。替代条件见 §1.4。**这条需要你拍板。** |
| Q2 | 「年终奖」要不要单独一个字段（而不是含在薪数里）？ | **不单设**。中国 offer 通用写法是「25k × 15」，年终奖就是多出来的那几个月；拆成两栏会逼用户做一次加法和一次减法，还容易填重。若将来要支持浮动年终奖（「3 个月，系数 0.5–1.5」），那是 P2 的另一套模型 |
| Q3 | 四维固定为「薪资 / 成长 / 城市 / WLB」够吗？要不要允许用户自定义维度？ | **固定四维，不开放自定义**。四个维度覆盖 90% 的实习生决策；开放自定义会带来「维度怎么存、旧维度怎么迁移、权重怎么重新归一」三件事，而用户的真实抱怨通常是「权重不对」而不是「维度不够」。自定义维度记在 `offerDecision.note` 里就够 |
| Q4 | 决策台要不要自动收录 `status='onboarded'` 的投递？ | **收录**，且已入职的在对比表里置灰只读。理由：入职半年后回看「我当时对比了谁」是这一版的核心价值之一，把已入职的排除掉等于把回看场景砍掉一半 |
| Q5 | 公司档案里「同名提醒」到什么程度？（COM-6） | **只提示，不拦截、不自动合并**。归一化规则沿用 `normalizeCompanyName`（去括号、去「有限公司」、全半角转换），命中只弹一次提示，用户点「否」就正常新建。**绝不自动合并**（同 `PRD-v0.2` §B.6「绝不按公司名单独合并」） |
| Q6 | 快记的词典要不要做成用户可编辑的词表？ | **不做**（本版）。用户可编辑词表 = 一套配置 UI + 一套持久化 + 一套「为什么我的词没生效」的支持成本，而基词表（今天/明天/周X/上午/下午/N点/N面/面试/笔试/回消息/挂了）已覆盖绝大多数说法。等真实误判反馈积累（CAP-14 的日志）再决定 |
| Q7 | 沉默清单的「批量放弃」要不要允许撤销超过 5 秒？ | **只给 5 秒 toast + 回收站 30 天双保险**。`dropped` 是终态但**进回收站**（既有机制），用户 30 天内都能恢复。不需要为它单独做长撤销窗口 |
| Q8 | 体积只剩 288 KB，四个模块全做完会不会挤爆？ | 按 §1.3 的 95 KB 预算不会（目标 ≤ 831 KB）。**若真超了，砍的顺序是**：OFF-10 导出 → CAP-14 调试日志 → COM-5 公司小计 → SIL-8 导出。**不砍**：OFF-3 加权分、CAP-5 公司三态、SIL-3 两步批量催问 —— 这三条是各模块的存在理由 |
| Q9 | `db.offerDecision` 只存一条，用户想保留「每次决策的历史」怎么办？ | **只存最新一条**。人的 Offer 决策一年 1–2 次，历史价值低于维护成本；真要留档，`offerDecision.note` 里写清背景 + 导出 Markdown 存自己网盘。若未来真需要，加 `decisions: OfferDecision[]` 是纯 additive 扩张，不破坏本版格式 |
